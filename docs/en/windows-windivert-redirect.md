# Windows WinDivert redirection principle

This document explains the internal mechanism by which anyproxy implements transparent proxy on Windows via WinDivert:
how packets are captured, NAT-rewritten, delivered to the local proxy, and then forwarded with the original destination restored.

Runtime dependencies (driver file placement, administrator privileges, etc.) are in [windows-winDivert.md](windows-winDivert.md).

## Architecture overview

```
Application (browser, etc.)
    │  original outbound packet: src=NIC_IP:clientPort → dst=server_IP:443
    ▼
┌─────────────────────────────────────┐
│  WinDivert kernel driver (NETWORK layer)     │
│  intercepts outbound TCP (80/443/...)       │
│  intercepts outbound UDP/53 (DNS hijack)     │
│  intercepts outbound UDP/443 (QUIC block)   │
└──────────────┬──────────────────────┘
               │ captured raw packet
               ▼
┌─────────────────────────────────────┐
│  Engine.process() (redirect.go)     │
│  parse packet → decide redirect → NAT rewrite  │
└──────────────┬──────────────────────┘
               │ rewritten packet: src=NIC_IP:natPort → dst=NIC_IP:ProxyPort
               ▼
┌─────────────────────────────────────┐
│  Local proxy listens :ProxyPort (proxy.go)  │
│  Accept connection → look up NAT table to restore destination  │
│  → proto.ForwardTCP routing/sniffing/forwarding   │
└─────────────────────────────────────┘
```

## Redirection flow (step by step)

### 1. WinDivert captures outbound packets

WinDivert registers a filter at the Windows kernel network layer, intercepting all outbound TCP packets
(as well as UDP/53 DNS, UDP/443 QUIC). The filter is generated by `candidateFilters()`, tried from the most
optimized to the simplest level by level, to ensure compatibility across WinDivert versions.

In non-all-ports mode, the filter only captures TCP packets whose destination port is in `RedirectPorts`
(default 80, 443), plus return packets whose source port equals `ProxyPort` (the proxy→application return traffic).

### 2. process() decision and classification

`Engine.process()` classifies each captured packet (redirect.go:193):

| Condition | Handling |
|----------|----------|
| impostor (packet injected by ourselves) | pass through directly, to avoid a capture loop |
| UDP/53 and hits a hosts hijack | locally construct a DNS answer to inject, drop the original query |
| UDP/443 and the destination IP is a hosts-hijacked IP | drop, to force QUIC to fall back to TCP |
| source port == ProxyPort | return packet, go through `rewriteReturn` to restore |
| destination port == ProxyPort and is loopback | pass through (own traffic not redirected) |
| upstream proxy address | pass through (avoid loop) |
| address in ExcludeIPs | pass through (`tun.bypassIPs` config) |
| source port in the egress segment (40001-49151) | pass through (anyproxy's own outbound connection, deterministically identified, see "Loop protection") |
| port claimed by socksGuard | pass through (fallback: fallback dial / external proxy process) |
| isDirect (loopback / skipPort / private when BypassPrivate) | pass through, no redirect |
| shouldRedirect and destination port in RedirectPorts | go through `rewriteForward` to redirect |

> The private network in `isDirect` is controlled by `BypassPrivate`; on Windows **`tun.windows.bypassPrivate`
> defaults to `true` when unset**: private/LAN/link-local (including VM/virtual NIC segments) all go direct, not into the engine;
> explicitly setting `false` lets private 80/443 enter the engine and follow router rules. `loopback` is always direct.
> See "Two connections and the direct determination" at the end.

### 3. rewriteForward: outbound packet → local proxy

`rewriteForward()` (redirect.go:324) rewrites the application's outbound packet into one destined for the local proxy:

```
original:  src=NIC_IP:clientPort  →  dst=server_IP:443

rewritten: src=NIC_IP:natPort     →  dst=NIC_IP:ProxyPort
         addr.SetLoopback(true)
```

Key operations:
- **allocate natPort**: allocate a unique port from the NAT table range `[10000, 40000]`,
  as the connection's identifier on the proxy side
- **rewrite source port** → natPort (lets the proxy reverse-lookup the destination by the remote port)
- **rewrite destination IP** → `p.srcIP` (i.e. this machine's NIC IP, not 127.0.0.1)
- **rewrite destination port** → ProxyPort
- **mark loopback**: `addr.SetLoopback(true)` lets WinDivert inject via the loopback path
- **recompute checksum**

### 4. Local proxy receives and restores the destination

`proxyServer` (proxy.go) listens on `:ProxyPort`, and after Accept:

1. Look up the NAT table by the connection's `RemoteAddr().Port` (i.e. natPort), restoring:
   - `dstIP` / `dstPort` (original destination)
   - `srcIP` (client source IP, for logging/statistics)
2. Rate-limit by destination IP (`MaxConnPerDomainPerSec`)
3. Hand to `proto.ForwardTCP`, where anyproxy's rule engine does:
   - SNI/Host sniffing to recover the domain
   - router.yaml rule matching
   - direct or forward to upstream proxy

### 5. rewriteReturn: return packet → restore original source

The proxy's returned packet (srcPort == ProxyPort) needs to be rewritten to "look like it came from the original server":

```
original return:  src=NIC_IP:ProxyPort  →  dst=NIC_IP:natPort

rewritten:   src=server_IP:443      →  dst=NIC_IP:clientPort
          addr.SetLoopback(false)
          addr.SetOutbound(false)  (inject as inbound packet)
          addr.SetIfIdx(...)       (restore to original NIC)
```

To the application, the connection looks like it is communicating directly with server_IP:443.

## Why listen on `:port` instead of `127.0.0.1`

This is the core design decision of the WinDivert redirection mechanism.

### Reason

`rewriteForward` rewrites the destination IP to the **original packet's source IP** (i.e. this machine's NIC IP),
not `127.0.0.1`:

```go
setDstIP(pkt, p.isIPv4, p.srcIP) // loop back to this host
```

So the packet reaching the TCP stack has a destination like `192.168.1.100:ProxyPort`,
not `127.0.0.1:ProxyPort`. If the listener only binds `127.0.0.1`,
the stack won't hand these packets to it, and the connection can't be established.

It must bind `:port` (i.e. `0.0.0.0:port` / `[::]:port`, all-interface dual-stack) to receive them.

### The security handling of binding all interfaces: only serve local redirected connections

Binding `:port` means that port is reachable on all NICs, seemingly allowing external hosts to connect directly. To avoid it becoming an exposed open port, `handle()` does a **source check** at Accept:

- A redirected connection has `rewriteForward` change the **destination IP to "the packet's own source IP"** (this machine's NIC IP), with the source IP unchanged — so a legitimate redirected connection's **remote IP is always equal to the local IP** (both are some NIC IP of this machine).
- When an external host connects directly to `NIC_IP:ProxyPort`, its remote IP is the attacker's IP, **not equal** to the local IP → rejected directly.
- Loopback (`127.0.0.1`/`::1`) sources are also allowed (local process, safe).

That is: serve only if `remote IP == local IP (or loopback)`, otherwise drop. This restricts the port to **local use only** without changing the NAT/loopback addressing logic. Even if the source IP is forged to bypass this check, the subsequent NAT table reverse-lookup by source port (natPort) still fails (an external connection's source port is not in `[10000,40000]` and has no corresponding entry), forming a second line of defense.

### Why not rewrite the destination IP to 127.0.0.1

Using `p.srcIP` as the destination has a key benefit: it **naturally preserves the IP protocol family**.

- Application connects via IPv4 → source IP is IPv4 → rewritten packet goes through the IPv4 stack
- Application connects via IPv6 → source IP is IPv6 → rewritten packet goes through the IPv6 stack

Fixing it to `127.0.0.1` would fail to handle IPv6 traffic, requiring an extra `::1` logic.

Using `p.srcIP` handles both IPv4 and IPv6 in one line, with no extra branch needed.

## NAT table

The NAT table (nat.go) is the core data structure of redirection, maintaining the mapping between
"the connection as seen by the application" and "the natPort on the proxy side".

### Data structure

```
natEntry {
    natPort    uint16      // unique proxy-side identifier (10000-40000)
    clientPort uint16      // application's original source port
    srcIP      netip.Addr  // original source IP (this machine's NIC IP)
    dstIP      netip.Addr  // original destination IP
    dstPort    uint16      // original destination port
    ifIdx      uint32      // NIC index (for return injection)
    subIfIdx   uint32      // sub-NIC index
    last       time.Time   // last active time
    closed     time.Time   // proxy connection end time (for fast reclamation)
}
```

### Bidirectional lookup

| Direction | Lookup key | Purpose |
|------|--------|------|
| forward (outbound) | `clientPort + dstIP + dstPort` | find or create a NAT entry, allocate natPort |
| lookupNat (return) | `natPort` | restore the destination by the proxy connection's remote port |

### natPort range

- Range: `[10000, 40000]`, 30000 available in total
- Deliberately below Windows' default dynamic port range (49152-65535), to avoid clashing with the system's own
  ephemeral ports
- Uses a rolling cursor allocation, scanning from the head after one full cycle

### Lifecycle and reclamation

| Event | Operation |
|------|----------|
| First outbound packet | allocate natPort, create entry |
| Subsequent packets | update `last` time |
| Proxy connection ends (FIN) | `markClosed()`, mark `closed` time, keep entry for FIN/ACK handshake |
| RST packet | `release()`, reclaim natPort immediately |
| GC cycle (5s) | reclaim entries closed over 10s; reclaim entries idle over 10min |

Keeping a closed entry briefly lets the TCP close handshake (FIN → ACK → FIN → ACK)
complete normally, without premature reclamation causing return packets to fail the lookup and be dropped.

## Loop protection

WinDivert intercepts all outbound TCP, including anyproxy's own connections.
Without protection, an infinite loop forms:

```
app → WinDivert intercept → local proxy → anyproxy outbound → WinDivert intercept → local proxy → ...
```

### Multi-layer protection

| Layer | Mechanism | Code |
|----|------|------|
| **egress source port segment** | anyproxy's outbound connections bind to the dedicated source port segment `[40001, 49151]`; process() passes packets in this segment directly | proto/egress.go, proto/dialer_windows.go, redirect.go |
| SOCKS Guard | listens on WinDivert SOCKET layer, records the proxy process's outbound source ports, process() passes them (fallback for fallback dial and external processes) | socksguard.go |
| Upstream exclusion | `SocksExcludeIP` / `SocksExcludePort` exclude connections to the upstream proxy | redirect.go:299 |
| IP exclusion | `ExcludeIPs` (`tun.bypassIPs`) exclude specified IP/CIDR | redirect.go:309 |
| loopback pass | packets with destination port == ProxyPort and loopback pass directly | redirect.go:232 |
| Rate limit | `MaxConnPerDomainPerSec` limits per-destination connection rate, as the last fallback | proxy.go:89 |

### egress source port segment (primary mechanism, consistent for IPv4/IPv6)

At the network layer, a packet cannot distinguish "a connection initiated by an app" from "a connection anyproxy dialed itself" — both have
the same source IP (this machine), same destination (the same server), and both are outbound 80/443. The only reliable distinction is
**source port + process identity**.

Approach: Windows' dialer (`tunDial`) binds every anyproxy outbound connection (to the direct server,
or to the upstream proxy) into the dedicated source port segment `[40001, 49151]`; in `process()`, any packet whose
source port falls in this segment is anyproxy's own outbound, passed directly, never re-captured.

Why this is a "root fix":

- **Deterministic**: the bind happens before `connect` sends the SYN, so there is no race.
- **IP-family-independent**: IPv4/IPv6 use the same segment and same check, naturally consistent.
- **Segment selection**: `[40001, 49151]` sits **above** the NAT port pool (10000-40000) and **below** Windows' dynamic/ephemeral port segment (49152-65535), so it neither clashes with the proxy's forged loopback ports nor with real app traffic (app outbound ephemeral ports start at 49152).

> Background: early versions relied only on SOCKS Guard (SOCKET-layer events) to identify anyproxy's own outbound. That event
> belongs to a different handle/goroutine than the NETWORK-layer SYN, with a race condition; **IPv6 direct connections stably lost
> this race**, causing anyproxy's own dial to the server to be repeatedly re-captured, forming an
> `app→proxy→egress→re-capture→proxy→…` infinite loop (symptom: the same target's connection count exploded within a second,
> throttled and idling by the 50/domain/second limit). Switching to the source port segment no longer depends on this event, root-causing the problem.

SOCKS Guard is kept as a fallback for two cases: ① fallback (unbound) dial when the port segment is exhausted;
② external proxy processes configured via `tun.windows.excludeProcs` (not going through anyproxy's dialer;
the config field is named `excludeProcs`, and the engine then fills it into `SocksProcessNames` for SOCKS Guard to match).

> Port segment trade-off: binding a fixed source port is affected by TIME_WAIT, and ports in the segment cannot be reused during TIME_WAIT (about 2-4 minutes on Windows). The segment has about 9000 ports; bind conflicts auto-retry on a different slot, and only when the whole segment is exhausted does it fall back to normal dialing (that one may loop, and is caught by the rate-limit fallback). It's enough for personal proxy scenarios;
> very high concurrent direct connections may occasionally fall back.

### How SOCKS Guard works

Network-layer packets don't carry process info, so SOCKS Guard uses WinDivert's SOCKET layer
(requires a newer WinDivert version):

1. Listen for SOCKET events (CONNECT / LISTEN / ACCEPT / CLOSE)
2. When a process LISTEN/ACCEPTs on ProxyPort, record its process name (e.g. `anyproxy.exe`)
3. When that process name initiates a CONNECT, record its source port
4. In process(), check if the source port is in the egress set; if so, pass it

It supports multi-process proxy suites (e.g. GUI + core separated like clash), identifying the whole proxy family by process name rather than
a single PID. Additional process names can be appended via `tun.windows.excludeProcs`.

If the SOCKET layer is unavailable (old WinDivert), the Guard is disabled,
relying only on the rate limiter as the loop fallback.

## IPv4/IPv6 handling

| Config | Behavior |
|------|----------|
| `IPv6: true` (default) | both IPv4 and IPv6 outbound packets are redirected to the local proxy |
| `IPv6: false` | IPv4 redirects normally; IPv6 within range is **dropped** (to prevent bypassing the proxy) |

IPv6 support comes from the "destination IP = source IP" design:
an IPv6 outbound packet's source IP is this machine's IPv6 address, and after rewrite the destination is also this machine's IPv6 address,
naturally going through the IPv6 stack, no special handling needed. The listener binds `:port` (dual-stack) to receive
both IPv4 and IPv6 connections simultaneously.

> anyproxy's own dial to the server (Leg 2) is also IPv6-compatible: it relies on the egress source port segment
> to pass, using the same segment and same check as IPv4, no longer depending on the SOCKET-layer event that loses the race on IPv6.
> The IPv6 direct loop problem was root-caused by this, see "Loop protection → egress source port segment".

## Two connections and the direct determination

Transparent proxy always has **two independent TCP connections**; don't confuse them:

- **Leg 1 = app → server** (browser → server:443): captured by WinDivert, NATted to
  `NIC_IP:ProxyPort` local listener.
- **Leg 2 = anyproxy → real server** (the one `ForwardTCP` dials out itself after deciding direct):
  this is the one bound in the egress port segment and passed directly by process().

"egress segment pass" passes Leg 2; the `NIC_IP:ProxyPort` listener serves Leg 1. They are
not the same thing, and the listener must be kept.

### Why Leg 1 must "take a hop", not be passed directly

At the moment the SYN is captured, anyproxy **does not yet know** whether this target should go direct or through the proxy:

- Domain-based rules (router.yaml, `default.target`, per-domain `host.proxy`) depend on
  **the TLS ClientHello SNI / HTTP Host**, and the first packet must wait for the TCP handshake to complete and the client to speak
  before it can be obtained.
- So this TCP must first be accepted locally as a "server" (only by landing on a `net.Listener`
  can you get a `net.Conn` to hand to `ForwardTCP`), read the first packet to sniff the domain, run the rules, possibly do
  remote DNS / counting / rate-limit / logging, **and only after deciding** know whether to go direct (→ Leg 2) or to the upstream proxy.

Until the handshake completes and SNI arrives, there's no way to decide "should this be passed" at the packet layer, so it must be redirected locally first.
This is the essence of transparent proxy, unavoidable.

### When "not redirecting" — direct determination by IP alone

When the **destination IP** alone determines direct, `process()` directly `return true` to pass, **without
NAT**, producing no Leg 1 transit:

| Condition | Code | Transit? |
|------|------|----------|
| loopback (127.0.0.0/8, ::1) | `isDirect` | no, pass directly |
| ports in `SkipPorts` | `isDirect` | no, pass directly |
| private / LAN / link-local (`BypassPrivate`, on by default on Windows) | `isDirect` | no, pass directly |
| `tun.bypassIPs` matched IP/CIDR | `isExcludedIP` | no, pass directly |
| destination port not in `RedirectPorts` (default non-80/443) | `shouldRedirect` | no, pass directly |

Only those **that must rely on the domain** have no choice but to take a hop to get the SNI.

### Which path does a private / VPN intranet address (e.g. `192.168.1.18`) take

On Windows `tun.windows.bypassPrivate` **defaults to `true` when unset**, so private addresses default to **direct, not into the engine**:

| Target (default `bypassPrivate=true`) | Determination | Result |
|------|------|------|
| `192.168.1.18:443` / `:80` / any port | `isPrivateOrLinkLocal` → `isDirect=true` | **no transit**, capture layer passes directly, direct to intranet |
| add `192.168.1.0/24` to `tun.bypassIPs` | `isExcludedIP` hit (also direct) | **no transit**, pass directly |

If explicitly set `tun.windows.bypassPrivate: false` (to let private also follow router rules):

| Target (`bypassPrivate=false`) | Determination | Result |
|------|------|------|
| `192.168.1.18:443` / `:80` | `isDirect=false`; 443/80 in `RedirectPorts` → `shouldRedirect=true` | **NAT forward (Leg 1)**: to local proxy, router rule determines (usually direct, Leg 2 dials that IP directly, egress segment passes without looping) |
| `192.168.1.18:22` (SSH), `:445` (SMB) and other non-80/443 | not in `RedirectPorts` → `shouldRedirect=false` | **no transit**, packet layer passes directly |

Choices:

- **Default (`bypassPrivate=true`)**: the whole private/LAN/VM blanket direct, simplest;
- want to **proxy a private target by router rules**: set `bypassPrivate: false`, let private 80/443 enter the engine;
- only want to **precisely allow certain segments** while the rest of private still follows rules: `bypassPrivate: false` + `tun.bypassIPs` listing the segments to go direct.

> Distinguish from "same-machine VPN escape": if the machine also runs a tunnel like OpenVPN, what needs excluding is
> **the VPN's transport endpoint** (server IP, via `tun.bypassIPs`) or **the VPN process**
> (via `excludeProcs`), to avoid `openvpn→server:443` being captured into a loop; this is a different matter from "accessing a host inside the VPN intranet", see [tun-dns-vpn-coexist.md](tun-dns-vpn-coexist.md).
