# nat-punch：最小化的 UDP 打洞验证工具

[derp-nat](../derp-nat/) 只能回答"derphole 那一整套机制最后有没有拿到直连"，中间套了太多层(DERP 信令 → 4 条并行 UDP lane → 1.2 秒打洞窗口 → 2 条 lane 的最低门槛 → QUIC 握手)，一旦失败根本分不清是哪一层的问题。这个工具把所有中间层全部剥掉，只测最底下那个问题：**两台各自在 NAT 后面的机器，能不能让一个 UDP 包互相到达。**

顺带也替代了之前用 `tcpdump` + `nc` 判断 NAT 类型的土办法，Windows 和 Linux 上用法完全一样(不需要 `nc`)。

零外部依赖，直接用仓库根模块，没有单独的 `go.mod`。

## 用法

需要**一到两台公网 VPS** 当反射器(reflector)。两台(且是**不同的公网 IP**)才能判断 NAT 类型，一台只能拿到自己的公网地址。

```bash
# 1. 在公网 VPS 上起反射器(有两台就都起，端口随意)
go run . -mode=reflect -listen=:3478

# 2. 在两台被测机器上分别运行(A 和 C 各跑一次)
go run . -mode=punch -reflect=<vps1-ip>:3478,<vps2-ip>:3478
```

第 2 步会先打印你的公网地址和 NAT 类型判定，然后停下来等你粘贴对端地址：

```
Your public address: 1.2.3.4:54321
NAT type: CONE (endpoint-independent mapping) — same mapping toward every reflector, punchable

Paste the peer's public address (ip:port) and press Enter:
```

**两台机器都要先跑到这一步**，然后把各自打印的公网地址粘贴到对方那边。打洞必须双方**同时**在发包才有意义——各自发出去的包，正是给对方在自己 NAT 上开返回通道的东西。

默认 `-duration=0` 表示**一直打到收到包为止**，就是为了消除"两边必须在几秒内对齐回车"这个约束：先启动的那台会一直发，等另一台起来自然就重叠上了，谁先谁后都行。收到第一个包即判定成功并退出(退出前会再多发 2 秒，好让晚启动的对端也确认到自己的接收方向)。想要固定时长可以显式传 `-duration=30s`，但那样就得自己保证两边窗口重叠——实测踩过这个坑：两边各跑 30 秒却错开了将近一分钟，两边都报 FAILED，其实根本没同时打过，白测一轮。

最后两边各自打印：

```
=== punch result ===
sent:     150
received: 143
verdict:  SUCCESS — a direct UDP path exists between these two hosts
```

`received > 0` 就是打通了。

只有**来自你粘贴的那个对端地址**的包才计入 `received`，反射器回包、以及其他无关流量都会被明确忽略并单独打日志——否则很容易把反射器自己的回包误判成"打洞成功"。如果收到的包来自对端 IP 但**端口不一样**，会专门提示一行：那是对方 NAT 重新分配了端口，即对称型 NAT 的典型表现。

## 结果里的 `peer live` 才是判断 FAILED 有没有意义的关键

打洞失败有两种完全不同的原因："对端根本没在跑"和"两边都在跑但网络不通"。靠两台机器的日志时间戳去对比是**靠不住的**——只要两边时钟没同步（实测遇到过差 62 秒的），就无法判断窗口有没有重叠，好几轮测试因此白做。

所以打洞期间工具会每 3 秒问一次反射器"对端现在活着吗"——反射器同时能看到两边，它的回答不受任何一方时钟影响。结果里对应 `peer live` 一行：

| `peer live` | `verdict` | 含义 |
|---|---|---|
| `yes` | SUCCESS | 打通了 |
| `yes` | FAILED | **两边都确认在跑还是不通——这才是真正的网络不通**（运营商级 NAT / 跨 ISP UDP 过滤） |
| `NO` | INCONCLUSIVE | 对端没在跑，这一轮不作数，重测 |
| `unknown` | — | 反射器是旧版本（不认识 `STATUS`），**需要在 VPS 上重新部署反射器** |

**反射器协议这次改过**：VPS 上如果跑的还是旧版本，`peer live` 会显示 `unknown` 并提示重新部署——务必先更新 VPS 上的反射器，否则拿不到这个判定。

## NAT 映射会过期，工具已自动保活

NAT 给 UDP 映射的空闲超时可能只有 30 秒到几分钟。你复制地址、切窗口、粘贴到另一台机器这段时间，如果 socket 一个包都没发，**映射可能已经过期**——打洞一开始 NAT 重新分配一个新端口，你之前贴给对端的地址就成了死地址，两边会一直打一个不存在的洞，日志上看就是 `sent` 一直涨、`received` 恒为 0，跟"NAT 类型不兼容"的表现一模一样，极难区分。

工具会在等你粘贴的这段时间每 10 秒向反射器发一个保活包，粘贴完成后再复查一次映射有没有变，正常会打印：

```
mapping still 36.251.232.138:42825 — the address your peer has is current
```

如果变了会明确警告，这时必须**重新交换地址**（用新的），否则这一轮测试没有意义：

```
WARNING: mapping changed ... -> ...  The address your peer is punching is DEAD
```

## 实测结论：两台国内家宽之间直连 UDP 不通（已排除全部干扰）

一次排除了所有已知干扰变量的实测，结果是**双向完全黑洞**：

| 项 | A（Windows，`36.251.232.138`） | C（Linux，`125.77.254.226`） |
|---|---|---|
| NAT 类型 | CONE（两个反射器观测到同一映射） | CONE（同上） |
| 映射复查 | `mapping still ...` 有效 | `mapping still ...` 有效 |
| 主机防火墙 | 已关闭 | — |
| 对端活跃确认 | 反射器确认 ACTIVE | 反射器确认 ACTIVE |
| 40 秒内发出 | 200 包 | 175 包 |
| **收到** | **0** | **0** |

反射器日志显示两边的状态查询在整个窗口内交替出现、全部 `ACTIVE`，即**两端确实在同一时间互打**——这一轮不存在"时间没对上"的可能。同时 C 侧 tcpdump 只有 `Out`、没有任何 `In`，A 的包没有到达 C 的网卡。

而两台机器各自跟公网 VPS 通信完全正常（反射器收发正常，[derp-nat](../derp-nat/) 里 A↔VPS、C↔VPS 打洞都成功过）。**两个端点都能跟公网服务器通，彼此之间双向全黑**，这是运营商级 NAT / 跨 ISP UDP 过滤的典型特征。

还有一个无法区分的细节（不影响结论）：包究竟是在中途被丢，还是 A 的 NAT 对 C 这个目标做了不同于对反射器的端口映射、导致包以非预期源端口到达 C 的路由器后被过滤——要分清得在 C 的路由器上抓包。两种情况的结果都一样：**这两个网络之间没有可用的直连 UDP 路径**。

这也解释了 [derp-nat](../derp-nat/) 里 A↔C 反复出现 `raw-punch-insufficient-paths`：两个独立工具指向同一个底层事实，不是 derphole 的参数或门槛问题。

> **对 anyproxy 的意义**：想靠打洞省掉服务端转发带宽，需要的正是"客户端(NAT 后) ↔ 订阅端(NAT 后)"这种双 NAT 直连，也就是这里测失败的拓扑；而已验证成功的是"NAT ↔ 公网 VPS"，那个方向服务端本身就是一个端点，打洞省不出带宽。所以打洞这条路对省带宽这个目标不可靠。相对地，[tunnel-hop](../tunnel-hop/) 那条路（中转那一跳从 TCP 换成 QUIC，解决 TCP-over-TCP 卡顿）完全不依赖打洞，走的就是已验证可用的拓扑。

## 关键设计：全程只用一个 socket

反射器观测到的地址、和后面真正打洞用的地址，必须是**同一个 NAT 映射**才有意义，所以整个流程(问反射器 → 等你粘贴 → 打洞)都在同一个 UDP socket 上跑，中途不退出。进程一旦重启，NAT 映射就变了，之前记下来的地址随即作废——这也是为什么工具设计成"停下来等粘贴"而不是"跑两次命令"。

## NAT 类型判定的原理和局限

同一个本地 socket 分别向两个**不同 IP** 的反射器发包，看两边观测到的外部端口：

- **端口一样** → 端点无关映射(Endpoint-Independent Mapping)，即 cone 型，可打洞
- **端口不同** → 对称型(Symmetric)，提前告诉对方的端口跟实际发包用的端口对不上，打洞基本没戏

**局限(重要)**：这个测试只验证了"映射(Mapping)"这一半，没验证"过滤(Filtering)"那一半——即映射建立之后，是不是**任何人**都能往这个端口发包进来(Full Cone)，还是**必须是你主动发过包的那个地址**才放行(Restricted / Port-Restricted Cone)。两边都测出 cone 但实际还是打不通，往往就是卡在过滤这一层，它对双方发包的时序要求更严。所以真正的结论要看 `punch result` 那一步的实测结果，NAT 类型判定只是辅助信息。

## Windows 注意

Windows 防火墙可能拦截入站 UDP。如果 NAT 类型判定正常(说明出站没问题)但 `received: 0`，先试试临时关闭防火墙、或者给这个程序放行入站 UDP，排除这个变量之后再下结论。
