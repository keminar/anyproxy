# nat-punch：最小化的 UDP 打洞验证工具

[derp-nat](../derp-nat/) 只能回答"derphole 那一整套机制最后有没有拿到直连"，中间套了太多层(DERP 信令 → 4 条并行 UDP lane → 1.2 秒打洞窗口 → 2 条 lane 的最低门槛 → QUIC 握手)，一旦失败根本分不清是哪一层的问题。这个工具把所有中间层全部剥掉，只测最底下那个问题：**两台各自在 NAT 后面的机器，能不能让一个 UDP 包互相到达。**

顺带也替代了之前用 `tcpdump` + `nc` 判断 NAT 类型的土办法，Windows 和 Linux 上用法完全一样(不需要 `nc`)。

零外部依赖，直接用仓库根模块，没有单独的 `go.mod`。

## 用法

需要**一到两台公网 VPS** 当反射器(reflector)。两台(且是**不同的公网 IP**)才能判断 NAT 类型，一台只能拿到自己的公网地址。

```bash
# IPv4：在公网 VPS 上起反射器(有两台就都起，端口随意)
go run . -mode=reflect -listen=:3478

# 在两台被测机器上分别运行(A 和 C 各跑一次)
go run . -mode=punch -reflect=<vps1-ip>:3478,<vps2-ip>:3478
```

IPv6 使用 `-network=udp6`，反射器和 A/C 必须使用相同的网络类型。IPv6 地址与端口组合时必须带方括号：

```bash
# VPS；:3478 在 udp6 下绑定 IPv6 通配地址 [::]:3478
go run . -mode=reflect -network=udp6 -listen=:3478

# A 和 C；有两台 IPv6 VPS 时同样可以填两个反射器
go run . -mode=punch -network=udp6 \
  -reflect='[2001:db8::10]:3478,[2001:db8::20]:3478'
```

随后交换的对端地址格式也是 `[IPv6]:端口`，例如 `[240e:1234::10]:54321`。`udp6` 通常没有 IPv4 NAT 端口转换，主要验证公网 IPv6 地址、UDP 端口以及主机/路由器/云安全组防火墙是否允许直连；程序仍会全程复用同一个 socket、持续互发并通过 reflector 确认双方是否同时处于测试阶段。

第 2 步会先打印你的公网地址和 NAT 类型判定，然后停下来等你粘贴对端地址：

```
Your public address: 1.2.3.4:54321
NAT type: CONE (endpoint-independent mapping) — same mapping toward every reflector, punchable

Paste the peer's public address (ip:port) and press Enter:
```

**两台机器都要先跑到这一步**，然后把各自打印的公网地址粘贴到对方那边。打洞必须双方**同时**在发包才有意义——各自发出去的包，正是给对方在自己 NAT 上开返回通道的东西。

默认 `-duration=0` 表示**一直打到收到包为止**，就是为了消除"两边必须在几秒内对齐回车"这个约束：先启动的那台会一直发，等另一台起来自然就重叠上了，谁先谁后都行。收到第一个包即判定成功并退出(退出前会再多发 2 秒，好让晚启动的对端也确认到自己的接收方向)。手动按 `Ctrl-C` 也会先打印截至当时的完整结果再退出。想要固定时长可以显式传 `-duration=30s`，但那样就得自己保证两边窗口重叠——实测踩过这个坑：两边各跑 30 秒却错开了将近一分钟，两边都报 FAILED，其实根本没同时打过，白测一轮。

最后两边各自打印：

```
=== punch result ===
attempted:   150
send ok:     150
send failed: 0
recv errors: 0
received:    143
peer live:   yes — its packets arrived here
verdict:     SUCCESS — a direct UDP path exists between these two hosts
```

`received > 0` 就是打通了。

只有**来自你粘贴的那个对端地址**的包才计入 `received`，反射器回包、以及其他无关流量都会被明确忽略并单独打日志——否则很容易把反射器自己的回包误判成"打洞成功"。如果收到的包来自对端 IP 但**端口不一样**，会专门提示一行：那是对方 NAT 重新分配了端口，即对称型 NAT 的典型表现。

## 结果里的 `peer live` 才是判断 FAILED 有没有意义的关键

打洞失败有两种完全不同的原因："对端根本没在跑"和"两边都在跑但网络不通"。靠两台机器的日志时间戳去对比是**靠不住的**——只要两边时钟没同步（实测遇到过差 62 秒的），就无法判断窗口有没有重叠，好几轮测试因此白做。

所以进入打洞循环时工具会立即问一次反射器"对端现在活着吗"，之后每 3 秒再问一次——这个 `STATUS` 查询本身也作为“我已经进入打洞循环”的心跳。反射器**只统计 `STATUS` 心跳**，不会把获取公网地址的 `WHOAMI` 或等待粘贴期间的保活误算成正在打洞，因此它的回答既不受双方时钟影响，也不会把“对端仅仅开着程序等待输入”误报为双方同时打洞。第一个对端打洞包也会立即发出，不需要先等待一个 `-interval`。结果里对应 `peer live` 一行：

| `peer live` | `verdict` | 含义 |
|---|---|---|
| `yes` | SUCCESS | 打通了 |
| `yes` | FAILED | **两边都确认在跑还是不通——这才是真正的网络不通**（运营商级 NAT / 跨 ISP UDP 过滤） |
| `NO` | INCONCLUSIVE | 对端没在跑，这一轮不作数，重测 |
| `unknown` | — | 反射器是旧版本（不认识 `STATUS`），**需要在 VPS 上重新部署反射器** |

**反射器协议改过**：VPS 上如果跑的还是旧版本，`peer live` 会显示 `unknown` 并提示重新部署——务必同时更新 VPS 上的反射器，否则拿不到可靠的活跃判定。反射器还会周期性清理过期活跃记录，长期运行不会因为见过的客户端越来越多而无限增长。

## NAT 映射会过期，工具已自动保活

NAT 给 UDP 映射的空闲超时可能只有 30 秒到几分钟。你复制地址、切窗口、粘贴到另一台机器这段时间，如果 socket 一个包都没发，**映射可能已经过期**——打洞一开始 NAT 重新分配一个新端口，你之前贴给对端的地址就成了死地址，两边会一直打一个不存在的洞，日志上看就是 `attempted` 一直涨、`received` 恒为 0，跟"NAT 类型不兼容"的表现一模一样，极难区分。

工具会在等你粘贴的这段时间每 10 秒向反射器发一个保活包，粘贴完成后再复查一次映射有没有变，正常会打印：

```
mapping still 36.251.232.138:42825 — the address your peer has is current
```

如果变了会明确警告、打印新地址并以 `INCONCLUSIVE` 中止，不再拿已知失效的地址继续打洞。这时必须**重新交换地址**（用新的）：

```
WARNING: mapping changed ... -> ...  The address your peer is punching is DEAD
Your NEW public address: ...
```

映射复查前只会在一个严格限制为 150ms 的窗口内清掉旧反射器回包。即使对端已经先开始高频打洞，也不会因为 socket 一直有包而卡在清空阶段；复查结束后本端会正常进入打洞循环。

## 实测结论：两台国内家宽之间直连 UDP 不通（已排除全部干扰）

一次排除了所有已知干扰变量的实测，结果是**双向完全黑洞**：

| 项 | A（Windows，`36.251.232.138`） | C（Linux，`125.77.254.226`） |
|---|---|---|
| NAT 类型 | CONE（两个反射器观测到同一映射） | CONE（同上） |
| 映射复查 | `mapping still ...` 有效 | `mapping still ...` 有效 |
| 主机防火墙 | 已关闭 | — |
| 对端活跃确认 | 反射器确认 ACTIVE | 反射器确认 ACTIVE |
| 40 秒内发出 | 200 包 | 175 包 |
| **收到** | **0** | **0** |

反射器日志显示两边的状态查询在整个窗口内交替出现、全部 `ACTIVE`，即**两端确实在同一时间互打**——这一轮不存在"时间没对上"的可能。同时 C 侧 tcpdump 只有 `Out`、没有任何 `In`，A 的包没有到达 C 的网卡。

而两台机器各自跟公网 VPS 通信完全正常（反射器收发正常，[derp-nat](../derp-nat/) 里 A↔VPS、C↔VPS 打洞都成功过）。**两个端点都能跟公网服务器通，彼此之间双向全黑**，这是运营商级 NAT / 跨 ISP UDP 过滤的典型特征。

还有一个无法区分的细节（不影响结论）：包究竟是在中途被丢，还是 A 的 NAT 对 C 这个目标做了不同于对反射器的端口映射、导致包以非预期源端口到达 C 的路由器后被过滤——要分清得在 C 的路由器上抓包。两种情况的结果都一样：**这两个网络之间没有可用的直连 UDP 路径**。

这也解释了 [derp-nat](../derp-nat/) 里 A↔C 反复出现 `raw-punch-insufficient-paths`：两个独立工具指向同一个底层事实，不是 derphole 的参数或门槛问题。

> **对 anyproxy 的意义**：想靠打洞省掉服务端转发带宽，需要的正是"客户端(NAT 后) ↔ 订阅端(NAT 后)"这种双 NAT 直连，也就是这里测失败的拓扑；而已验证成功的是"NAT ↔ 公网 VPS"，那个方向服务端本身就是一个端点，打洞省不出带宽。所以打洞这条路对省带宽这个目标不可靠。相对地，[tunnel-hop](../tunnel-hop/) 那条路（中转那一跳从 TCP 换成 QUIC，解决 TCP-over-TCP 卡顿）完全不依赖打洞，走的就是已验证可用的拓扑。

## 关键设计：全程只用一个 socket

反射器观测到的地址、和后面真正打洞用的地址，必须是**同一个 NAT 映射**才有意义，所以整个流程(问反射器 → 等你粘贴 → 打洞)都在同一个 UDP socket 上跑，中途不退出。进程一旦重启，NAT 映射就变了，之前记下来的地址随即作废——这也是为什么工具设计成"停下来等粘贴"而不是"跑两次命令"。

## NAT 类型判定的原理和局限

同一个本地 socket 分别向两个**不同 IP** 的反射器发包，看两边观测到的外部端口：

- **端口一样** → 端点无关映射(Endpoint-Independent Mapping)，即 cone 型，可打洞
- **端口不同** → 对称型(Symmetric)，提前告诉对方的端口跟实际发包用的端口对不上，打洞基本没戏

**局限(重要)**：这个测试只验证了"映射(Mapping)"这一半，没验证"过滤(Filtering)"那一半——即映射建立之后，是不是**任何人**都能往这个端口发包进来(Full Cone)，还是**必须是你主动发过包的那个地址**才放行(Restricted / Port-Restricted Cone)。两边都测出 cone 但实际还是打不通，往往就是卡在过滤这一层，它对双方发包的时序要求更严。所以真正的结论要看 `punch result` 那一步的实测结果，NAT 类型判定只是辅助信息。

## 打洞怎么应对"端口受限"这层过滤

不用这个工具，光用 `nc` 也能手工验证一遍这个过滤规则，完整流程分三步：

```bash
# 1. B（VPS）：启动反射器，占住 3478 端口
./nat-punch -mode=reflect -listen=:3478
```

```bash
# 2. A（内网机）：发一个包给 B，B 会把 A 的公网映射地址回给 A
nc -u <vps-ip> 3478
# 输入任意内容回车发送，A 的终端会打印类似这样一行：
#   <a-ip>:46435
# 这就是 A 在 B 眼里的公网地址。这个 nc 进程先别退出——
# 一退出映射可能就变了，后面 B 回包会找不到这个地址。
```

**"先别退出"不是因为没指定本地端口，`-p` 也补不上这个洞。** 退出重启、用 `-p` 固定本地端口、换一个目的 IP 再发，能不能拿到同一个公网端口，分两种情况：

- 如果这台 NAT 是**对称型(APDM)**：外部端口本来就是跟目的地址绑在一起分配的，换一个目的 IP 必然拿到新端口，跟本地端口是否固定完全无关，这个思路直接不成立。
- 如果是**端点无关映射(CONE/EIM)**：理论上换目的地不影响外部端口分配。但退出期间这条映射在 NAT 表里的空闲计时并没有停——只要退出到重启的空档没超过 NAT 的 UDP 空闲超时（可能只有 30 秒到几分钟），重新绑定同一个本地端口大概率能拿回同一个外部端口；一旦超时，NAT 会把这次重新绑定当成全新映射来分配，是否分回原来那个端口，取决于这台 NAT 是不是"端口保留型"(port-preserving)——消费级路由器大多是，运营商级 CGNAT 端口紧张时未必，这一点没法提前判断，只能实测。

**另外，`nc` 本身没有任何自动保活机制**——只有往 stdin 敲字符回车才会真正发一个包、给这条 NAT 映射的空闲计时器续一次命。"进程先别退出"只保证本地端口不被系统释放、并且随时能接收 B 的回包，**不等于**"映射会一直有效"。如果中间等待时间比较长，光靠不退出防不住空闲超时，稳妥做法是每隔几秒手动敲个字符补发一个空包。

```bash
# 3. B（VPS）：Ctrl+C 停掉第 1 步的反射器进程，腾出 3478 端口，
#    然后用同一个端口（3478）回包给 A 的映射地址
nc -u -p 3478 <a-ip> 46435
# 输入内容回车发送
```

如果 A 的终端上收到了第 3 步发的内容，就验证了那条过滤规则：**发起方（这里是 B）只要主动往 A 认可的那个 `ip:port` 发包，就能穿透 A 的 NAT**——不是端口凑巧对上了，是 B 必须复用 A 之前联系过的那个端口（3478）发起，才算"A 认可的发起方"。第 3 步如果用一个新端口发（不加 `-p 3478`，或者不停第 1 步的反射器、另开进程用别的端口发），十有八九会像最初遇到的情况一样，A 什么都收不到。

要注意这个手工流程跟真正的三方打洞（A/B/C）不是一回事：这里是**反射器自己（B）回包**给 A，验证的是"B 主动发起能不能到 A"；而真正打洞是 **C**（A 事先从没联系过的第三方）往 A 发包，靠的是 C 自己也同时往 A 的地址主动发一发，给自己在 A 这边"开洞"——A 和 C 都要各自主动发，不能只有一边发。上面这步 `nc` 测试只验证了过滤规则本身，不能代替真正的 A-C 双向打洞测试。

放到真正的 A(内网) / B(VPS 反射器) / C(内网) 三方打洞里，这个坑天然不存在，因为过滤规则是**按对端分别判断**的，不是"必须等于 B 的端口"：

- **映射这一层**：A 全程复用同一个本地 socket（问 B、也是直接打给 C），如果 A 是端点无关映射(CONE)，这个 socket 对外的公网端口永远是同一个 `A_pub_port`，不管发给 B 还是发给 C。这保证了 B 转告给 C 的"A 的地址"，在 A 真正发包给 C 时依然有效——这一层要求的是"A 自己的端口不漂移"，跟 C 用什么端口无关。
- **过滤这一层**：A 的 NAT 只放行"A 自己主动发过包"的那个地址。A 跟 B 通信开的洞（放行 `VPS_IP:3478`）和 A 跟 C 打洞开的洞（放行 `C_pub_ip:C_pub_port`）是两条独立的洞，互不依赖。真正让 C 的包能过 A 的 NAT 的，是 A 自己往 `C_pub_ip:C_pub_port` 主动发的那一发包，不是"C 用的端口恰好等于 3478"。C 那边同理。

也就是说，**端口受限锥形(Port-Restricted Cone) 理论上是可以打成功的**——这正是打洞技术本来要解决的场景，跟 Full Cone、Address-Restricted Cone 一样可穿透，真正打不穿的只有对称型(Symmetric)。前提是双方 Mapping 都是 CONE 型（用上面的判定验证），并且双方**同时**互相主动发包，各自给对方开好洞。

**但现实会比理论多一层**：上面"两台国内家宽之间直连 UDP 不通"那次实测，两边都是 CONE、时序也用反射器确认过确实同时在打，最后依然双向全黑——说明运营商级 NAT(CGNAT)、跨 ISP 链路上的 UDP 过滤，可能在两台机器各自的路由器之外再叠一层，这层无法靠打洞测出来也绕不过去。所以"端口受限锥形理论上可打洞"是对的，但不代表所有实际网络路径都能打通，最终还是要看 `punch result` 的实测结果。

## TCP 打洞（`tcp-punch` / `tcp-reflect`）

跟前面的 UDP 打洞是完全不同的机制，不是协议换个名字：UDP 打洞靠"发包出去就让 NAT 放行回包"；TCP 没这个天然规则，靠的是 **TCP 同时打开(Simultaneous Open)**——双方几乎同时往对方发 SYN，两个 SYN 在半路交叉，TCP 协议栈会当成"同时打开"直接建连，不分谁是客户端谁是服务端。

```bash
# VPS 上：TCP 反射器，跟 UDP 反射器是两个不同的东西（很多 NAT 对 TCP/UDP 用不同端口池，
# UDP 测出的映射不能当 TCP 的用），默认端口 3479，别跟 UDP 反射器的 :3478 搞混
go run . -mode=tcp-reflect -tcp-listen=:3479

# 两台被测机器上分别运行
go run . -mode=tcp-punch -tcp-reflect=<vps-ip>:3479
```

同样先打印自己的公网 TCP 地址，然后等你粘贴对端的。**这里没有 UDP 版那个"一直等到收到包为止"的保活机制**——TCP 是连接导向的，本地端口从探测阶段到打洞阶段全程固定复用（`SO_REUSEADDR`），粘贴完立刻开始，两边尽量卡到同一时间点。跑完打印：

```
=== tcp punch result ===
verdict: SUCCESS — a direct TCP path exists between these two hosts (...)
```

### 值得试，但别抱太大期望

前面那次决定性的 UDP 实测已经证明：两边 NAT 类型正常(CONE)、映射稳定、反射器确认双方全程都在打，包依然全黑——这更像是路径上某个设备（运营商大内网、跨 ISP 审计设备）在无差别丢包，而不是"NAT 映射搞不定"。这种**路径级过滤通常不分协议**，UDP 通不过，TCP 大概率也通不过。

但这个测试成本很低，而且不是纯粹重复——如果 TCP 意外打通了，说明运营商是**专门**针对 UDP 做的限流/过滤（不少地方确实会把陌生 UDP 当成 P2P/游戏加速器流量特殊处理），是个有价值的新发现，值得跑一次确认。

### 实现细节（关心可靠性可以看看，不关心可以跳过）

- 本地端口全程固定（`-tcp-local`，不填会自动挑一个并打印出来），因为要在同一个端口上"边监听、边反复往对端发起连接"——这是靠 `SO_REUSEADDR` 做到的，Windows 和 Unix（Linux/macOS）的系统调用签名不一样，分别在 `reuseaddr_windows.go` / `reuseaddr_unix.go` 里实现
- 出向那边不是发一次就等，是每 300ms 重连一次、最长等 700ms 超时，一直试到 `-tcp-duration`（默认 60s）或者收到入向连接为止——因为不知道对面的 NAT 洞什么时候才真正打开
- 已在本机回环测过监听 + 出向两条路径都能正常工作（编译也过了 Windows/Linux/macOS 三个平台），但"回环测试通过"只能验证代码逻辑没写错，**不代表跨真实 NAT 会成功**，这个只能真机测

## Windows 注意

Windows 防火墙可能拦截入站 UDP。如果 NAT 类型判定正常(说明出站没问题)但 `received: 0`，先试试临时关闭防火墙、或者给这个程序放行入站 UDP，排除这个变量之后再下结论。
