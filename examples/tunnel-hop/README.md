# tunnel-hop：只测"中间那一跳"该用 TCP 还是 QUIC

给 anyproxy websocket 隧道数据面要不要从 TCP 换成 QUIC([见此前讨论](../../docs/websocket.md))做一次量化对比，目标是 mstsc 远程 Windows 的卡顿问题。独立小程序，**不接入 anyproxy 主代码**，也不需要 [derp-nat](../derp-nat/) 那套 NAT 打洞依赖——这里只测"两台已知地址、能互相拨通的机器之间，中间这一跳用什么协议"，跟打不打得通直连无关。

## 测的是什么，不是什么

**不测**：真实 mstsc.exe + 真实 Windows RDP 目标机的主观流畅度——那需要真实 RDP 环境、自动化客户端、量化渲染帧时序，超出这个 examples 的范围，而且"流畅"本身就很难自动量化。

**测的是**：中间那一跳分别用 TCP 中继、QUIC 中继时，同一段真实网络路径下，一段**模拟 RDP 屏幕更新特征的合成流量**(固定节奏发小包，默认每 20ms 一个 512 字节包，对应约 50fps 的更新频率)传过去之后，到达间隔的分布——尤其是**停顿(stall)**：相邻包到达间隔超过阈值(默认 150ms，人眼能感知卡顿的大致门槛)的次数和总时长。

这样测的道理：TCP 保证严格有序交付，中间一丢包，后面所有数据都得等这个包重传完才能往上交付，对高频小包的交互流量就是几百毫秒到几秒的卡顿。QUIC 按 stream 独立处理丢包恢复，同样丢包情况下更不容易出现这种"全部卡住等一个包"的效应。这个"停顿分布"比稳态平均延迟更能预测 RDP 卡不卡，也是这个 examples 唯一要量化的东西。

## 范围说明(诚实标注，别当成完整还原)

anyproxy 现在裸 TCP 转发(路径 B)的真实结构是三层：`真实 RDP 客户端的 TCP 连接 → websocket(TCP) 隧道 → 真实 RDP 目标机的 TCP 连接`，两端各自的 TCP 连接也有自己独立的重传逻辑，跟中间隧道的重传叠加会加重"TCP-over-TCP"效应。这个 examples 为了简单，**没有还原两端那两层真实 TCP**，只测中间这一跳本身——也就是这次设计讨论里唯一要改的那个变量。这意味着实测出来的停顿数字，大概率比 anyproxy 真实生产环境里的更轻——但 TCP 中继 vs QUIC 中继**谁更差**这个相对结论是成立的，只是绝对数值别直接当成"接入 anyproxy 后能改善多少"的精确预测。

## 怎么跑

**必须在两台真实机器之间跑，走一条真实有损的网络路径**，才有意义——回环测不出丢包效应(见下面本地冒烟测试)。可以直接复用你之前测 DERP 打洞时用过的那台内网机器 C + VPS，这条链路已经验证过有真实丢包/抖动。

```bash
# 近端(模拟 RDP 客户端所在位置，比如你手上的机器) — 监听
go run . -side=sink -hop=tcp -listen=:9100 -stall=150ms

# 远端(模拟 RDP 目标机位置，比如 VPS 或内网机器 C) — 拨过去
go run . -side=source -hop=tcp -connect=<近端IP>:9100 -duration=60s
```

跑完看近端打印的 `sink report`。然后**换端口、换成 `-hop=quic`，其他参数不变，紧接着再跑一次**，尽量让两次测试面对的网络条件接近：

```bash
go run . -side=sink -hop=quic -listen=:9200 -stall=150ms
go run . -side=source -hop=quic -connect=<近端IP>:9200 -duration=60s
```

对比两次的 `p95`/`p99`/`max gap` 和 `stalls` 那几行——QUIC 那次的停顿次数/总停顿时长明显更少，就说明这个方向值得投入；如果两边差不多，说明这条链路本身丢包率不足以体现 TCP-over-TCP 的劣势(比如两台机器都在同一运营商骨干网内、丢包率本来就很低)，换一条更差的链路(比如手机热点)再试。

参数可调：`-rate`(包间隔，默认 20ms)、`-payload`(包大小，默认 512 字节，最小 8 字节)、`-duration`(测试时长)、`-stall`(卡顿判定阈值)。

## 本地冒烟测试(只验证代码没写错，测不出真实差异)

TCP 和 QUIC 两种 hop 各自在本机回环跑了一次(3 秒、20ms 节奏)，确认握手/收发/统计逻辑没问题：

```
tcp:  p50 19.9ms / p95 20.8ms / max 21.3ms / stalls(>30ms): 0
quic: p50 20.0ms / p95 20.6ms / max 20.8ms / stalls(>30ms): 0
```

回环网络几乎不丢包，两边数字几乎一样，符合预期——但这**不代表两种方案没差别**，真正的差别只有在有真实丢包的链路上才会显现出来，必须按上面的步骤跨机器实测。

## 依赖

只用了 `github.com/quic-go/quic-go`，没有引入 [derp-nat](../derp-nat/) 那套 Tailscale 技术栈，`go.mod` 单独成模块，不影响仓库根模块。QUIC 一侧用的是运行时生成的自签证书 + 跳过校验(`InsecureSkipVerify`)，只是为了这次测传输层表现方便——真要接入 anyproxy，证书这块需要按[之前讨论的一次性凭证方案](../../docs/websocket.md)正经做鉴权，不能照搬这里的写法。
